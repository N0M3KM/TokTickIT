# Staff and administrator dashboard queries

Feature 23 uses the shared Bangkok date window and one RepeatableRead snapshot for its global operational metrics, recent tickets and current-user actions. Administrators use the same global ticket scope as staff; the session actor ID determines both owned tickets and assigned actions. Creator/performer and ticket owner do not determine action assignment.

Action totals count active assigned actions only on active parents. Related ticket totals and queue filters use EXISTS rather than joining child rows, so multiple actions cannot inflate ticket counts. Status groups include all eight statuses; priority groups include all four priorities on active tickets. Missing groups are zero-filled in documented enum order. Both preview lists are capped at five; action descriptions are capped at 120 Unicode code points and action links include the direct action anchor.

`buildStaffDrilldown` scopes only dashboard-specific query fields; the queue route validates the remaining supported filters and combines both predicates with AND. Recently updated views use updatedAt descending with an ID tie-breaker. All normal queue sort options also include an ID tie-breaker. Dashboard identity/time overrides and malformed new drill-down filters are rejected. Existing non-dashboard queue filter behavior is retained.

The dedicated real PostgreSQL suite independently reconciles metrics, every bucket, distinct parents, previews and queue totals; checks role/identity boundaries and a concurrent commit under the snapshot; and benchmarks both dashboards against an additional isolated database with exactly 1000 tickets and 3000 actions. It observes actual SQL counts through a query-logged Prisma client. The application database is never used for these fixtures. UI/browser and final release evidence are recorded separately.

Backend verification on 31 October 2026: the disposable runner passed 75 real PostgreSQL tests (21 staff, 31 requester and 23 retained workflow tests), including genuine global empty-bucket checks before seeding the isolated performance database. Nine staff helper tests and the server TypeScript check passed. With five warmups and thirty measured requests per endpoint on the exact 1000-ticket/3000-action database, requester p50/p95 were 10.72/13.98 ms, maximum JSON payload 3373 bytes, with nine SQL queries per request. Staff p50/p95 were 18.05/21.97 ms, maximum JSON payload 3862 bytes, with twelve SQL queries per request. SQL counts were constant across measured requests. The distinct-parent EXPLAIN ANALYZE used the action assignee/status index and Ticket primary key, with 1.881 ms execution time. These are local smoke measurements, not production service guarantees.
